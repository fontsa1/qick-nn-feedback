This page summarises the two rebuilds: build 1 runs the tProc core at QICK's stock clock, build 2 puts an LDA core in
NN_live's place. Each build changes one thing from v1.44.

- **Board runs:** in `RESULTS_BOARD_2026-11-18.md`.

- **Status:** both bitstreams are complete, but **neither meets setup timing**.

## Build 1: tProc at 245.76 MHz

### Why v1.44 runs the core at 200 MHz

- **The clock:** the tProc runs from QICK's `clk_core`, set to 200 MHz.
- **The reason was margin.** An earlier static-timing study judged 200 MHz
  borderline. The tProc's out-of-context run closed at 5.0 ns with WNS +0.422 ns, an implied Fmax of about 218 MHz; its worst
  path was D_MEM BRAM → reg_bank.
- **The routed v1.44 margin** was +0.320 ns.

### Result

- **The core clock closes at stock 245.76 MHz** with +0.024 ns of slack. Its worst path is D_MEM RAMB36 →
  `reg_bank/sreg_dt_reg` (3.804 ns, 8 levels), the same path the out-of-context run found.
- **The failures are a placement side effect, not the tProc:**
  - `axis_dyn_readout_v1_0/1/2`: 219, 261 and 142 endpoints;
  - seg_stamp_0: 15;
  - axis_avg_buffer: 7;
  - register_slice_2/3: 6;
  - weighted_buffer: 4;
  - cdcsync: 3;
  - live_res_cdc_1: 1.
  - The worst path is RFADC `FABRIC_CLK` → `axis_register_slice_2/storage_data1_reg[25]_replica`. NN_live_0's worst
    path is at −0.001 ns.
- **Utilization:** whole design LUT 252,209 / FF 284,732 / BRAM 500 / DSP 542 (Table III: 252,806 / 285,071 / 500 / 542).
  NN_live uses 1,342 LUT / 1,222 FF and the loop logic 1,949 / 4,329.
- **Script changes needed for the board:**
  - the banner string;
  - the f_core check. `qick_functional_test.py` T00 hard-codes 200 MHz, so `qick_functional_test_fcore.py` takes
    `QICK_EXPECT_FCORE=245.76`.
- **Next remedy, prepared but not run:** an incremental place and route guided by v1.44's routed dcp (remedy #10):
  `b1_remedy_incremental.tcl` and `$QICK_WORK/remedy_incr_b1.bat`. It takes about 4 h.

## Build 2: LDA through the gate

### The model and its fixed-point form

- **The model:** lda_99400.py's box576 model, refitted on training rows only.
  - Class moments come from rows [0, 180k) of `0528_X_train_box_calibrated`.
  - The ridge (1e-3, validation 96.145%) was chosen on rows [180k, 200k).
  - The threshold comes from the training scores (t = −0.67194).
  - It reproduces `lda_99400_preds` box576 on every test row.
- **Fixed point:**
  - The weights are 16-bit, round(w·2²²).
  - The I and Q accumulators are exact integers.
  - The decision is S ≥ floor(t·2²²)+1.
  - res_o carries a saturated pseudo-logit, so the tProc threshold (fb_thr = 16) and the host rules are unchanged.
- **The core's interface:** ports, framing and the record layout are the same as NN_live. Header word 3 is "LDA1".
- **Quantization loss:** 1 flip against float LDA in 99,400 on the headline mosaic, 1 on A_full and 0 on B_full.

### Verification and HLS results

- **csim:** bit-exact against `lda_model.py` on all 200,000 stored v1.44 gate windows, covering records, header and both
  framing faults.
- **RTL sim** (`rtl_sim/tb_lda.sv`): PASS.
- **Latency, last sample → res_o:** 8 cycles = 14.5 ns, against NN_live's 9 cycles = 16.3 ns on the same testbench.
- **Routed size:** 763 LUT / 669 FF / 2 DSP / 0.5 BRAM, against NN_live's 1,343 / 1,221 / 4 / 0.5.

### Timing

- **The failures:**
  - mostly stock readouts: dyn_readout_v1_0/1/2 with 70, 303 and 200 endpoints, and register_slice_2 with 12;
  - boxcar_tap_0: 7;
  - **the LDA core itself: 5**, on the path n counter → 576-deep LUTRAM ROM decode → `LROM_U/q0_reg` (5 levels, −0.065 ns).
  - The worst path overall is boxcar_tap → axis_avg_buffer_1 (−0.094 ns).
- **Utilization:** whole design LUT 251,907 / FF 284,069 / BRAM 500 / DSP 540. The loop logic uses 1,953 / 4,425.

### The fix: LDA_live 1.1, prepared but not built

- **The change:** the ROM moves to block RAM with latency 2 (`lda_gate/hls11`).
- **Verified:** csim is bit-exact on 200k windows, and the RTL sim passes at **9 cycles, the same as NN_live**.
- **Build 2b** (TAG `v1.44lda11`, fresh QICK copy `q3`) is staged in `make_b2b.bat` / `build_b2b.bat` and the
  `*_lda11.tcl` scripts. It takes about 6 h.
- **Why it is the better control:** the loop would differ from v1.44 only in the classifier, with the same latency.
  If 2b is used, set `QICK_RES_MINUS_LAST=9` in `latency_protocol_lda.py`.
